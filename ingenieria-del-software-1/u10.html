01Repaso

Texto base de cátedra: Pressman (2010), capítulo 10. Las fuentes de acceso abierto te permiten profundizar.

Componente

Pressman retoma la definición de la especificación UML: una parte modular, desplegable y sustituible de un sistema, que encapsula su implementación y expone un conjunto de interfaces (Pressman, 2010, cap. 10).

Tres visiones

Orientada a objetos: un componente es un conjunto de clases que colaboran. Tradicional: un módulo funcional que integra lógica de procesamiento y estructuras de datos. Relacionada con el proceso: se construye a partir de componentes existentes y reutilizables (Pressman, 2010, cap. 10).

Principios

Abierto-cerrado (OCP): abierto a la extensión, cerrado a la modificación. Sustitución de Liskov (LSP): una subclase debe poder reemplazar a su clase base. Inversión de dependencias (DIP): depender de abstracciones, no de concreciones. Segregación de interfaces (ISP): varias interfaces específicas son mejores que una general. Para el empaquetado: equivalencia de liberación y reutilización (REP), cierre común (CCP) y reutilización común (CRP) (Pressman, 2010, cap. 10).

Lineamientos

Convenciones de nombres para componentes e interfaces tomadas del dominio del problema, representación explícita de las interfaces, dependencias modeladas de izquierda a derecha y herencia de abajo (clases derivadas) hacia arriba (clases base) (Pressman, 2010, cap. 10).

Cohesión

Mide cuánto se concentra un componente en una sola cosa. Pressman, siguiendo a Lethbridge y Laganière, describe la cohesión funcional (una sola función), de capa (una capa usa los servicios de la inferior) y de comunicación (operaciones que acceden a los mismos datos) como las más deseables, y otras más débiles como la secuencial, la de procedimiento, la temporal y la de utilería (Pressman, 2010, cap. 10).

Acoplamiento

Mide cuánto depende un componente de otros. Las categorías van de las más fuertes y peligrosas a las más débiles: de contenido (un componente modifica datos internos de otro), común (comparten variables globales), de control (uno pasa banderas que dirigen la lógica del otro), de sello, de datos, de llamada a rutina, de uso de tipo, de inclusión o importación y externo (Pressman, 2010, cap. 10). Ocultar información, como propuso Parnas, es la mejor defensa contra el acoplamiento (Parnas, 1972).

Cómo se diseña

Se identifican las clases de diseño del dominio del problema y de la infraestructura; se detallan sus atributos, operaciones e interfaces; se describen los mensajes entre clases colaboradoras; se especifican las fuentes de datos persistentes; se representa el comportamiento con diagramas de estados; y se refina y revisa continuamente (Pressman, 2010, cap. 10).

No confundas

Bajo acoplamiento no es «ningún acoplamiento». Los componentes tienen que colaborar; lo que se busca es que dependan de interfaces estables y no del interior de los demás (Pressman, 2010, cap. 10).

OCP no prohíbe corregir errores. Dice que agregar comportamiento nuevo no debería obligar a modificar el código que ya funciona.

Con IA, con criterio

Pide a un asistente de IA que «agregue el envío por SMS» al ejemplo del lado «Antes» y mira qué hace: muchas veces agrega un if canal == "sms" dentro de la lógica de turnos, aumentando el acoplamiento de control. El principio abierto-cerrado te dice qué pedirle en cambio (Pressman, 2010, cap. 10).

02Caso aplicado

Caso transversal · Turnos USF

Una Unidad de Salud Familiar (USF) de barrio atiende clínica general, pediatría y control prenatal. Hoy los turnos se reparten por orden de llegada: la gente hace fila desde la madrugada y muchas veces vuelve a su casa sin ser atendida. La directora de la USF, el equipo de enfermería y la región sanitaria quieren un sistema de turnos: pedir turno por la web o por mensajería, una pantalla en la sala de espera y reportes mensuales de atenciones.

Este caso acompaña las 11 unidades. En cada una lo miras con los conceptos nuevos.

El mismo pedido de turno, con dos diseños de componentes (pseudocódigo en Python).

class GestorUSF:
    def pedir_turno(self, cedula, dia):
        conexion = mysql.connect("servidor-usf")      # base de datos fija
        ...                                           # calcula horarios libres
        whatsapp.enviar(cedula, "Su turno es ...")     # canal fijo
    def imprimir_lista_del_dia(self): ...
    def reporte_region_excel(self): ...
    def cambiar_clave_usuario(self): ...

Una sola clase hace de todo: cohesión baja. Depende directamente de MySQL y de WhatsApp: acoplamiento alto. Cambiar el canal de mensajería obliga a modificar la lógica de turnos.

class Notificador:                  # abstracción (interfaz)
    def enviar(self, paciente, mensaje): ...

class NotificadorWhatsApp(Notificador): ...
class NotificadorSMS(Notificador): ...

class ServicioTurnos:
    def __init__(self, agenda, repositorio, notificador):
        self.agenda = agenda                 # depende de abstracciones,
        self.repositorio = repositorio       # no de implementaciones
        self.notificador = notificador

    def pedir_turno(self, paciente, dia):
        horario = self.agenda.primer_libre(dia)
        turno = self.repositorio.guardar(paciente, horario)
        self.notificador.enviar(paciente, turno.resumen())
        return turno

Cada clase tiene un propósito: cohesión funcional. ServicioTurnos depende de abstracciones (principio de inversión de dependencias) y se puede agregar un canal nuevo sin modificarlo (principio abierto-cerrado).

03Actividades de práctica

Cada actividad indica cuándo terminaste. No pases a la siguiente hasta cumplirlo.

Actividad 1 · Diagnóstico de cohesión y acoplamiento

Individual · 30 min

Toma una clase o módulo de un trabajo práctico anterior (de cualquier materia).

  1. Lista sus operaciones y clasifica su cohesión con las categorías de la unidad.
  2. Lista de qué depende y clasifica cada acoplamiento.
  3. Propón una división en dos o tres componentes con cohesión más alta.
  4. Indica qué principio (OCP, LSP, DIP o ISP) aplicaste y dónde.

Terminaste cuando tienes la cohesión y cada acoplamiento clasificados con su nombre, una división propuesta y un principio aplicado en un punto concreto.

Actividad 2 · Componentes del TPI

En equipo de trabajo · 40 min

Partan de la arquitectura elegida en la Unidad 9.

  1. Elijan un componente de la arquitectura y detallen sus clases de diseño.
  2. Definan sus interfaces con nombres del dominio.
  3. Identifiquen un punto de variación probable y protéjanlo con una abstracción.
  4. Dibujen el diagrama de clases con dependencias de izquierda a derecha.

Terminaste cuando el componente tiene clases con atributos y operaciones, interfaces explícitas y un punto de variación protegido por una abstracción.

Conexión con el TPI. Cada componente del diseño del TPI debe poder rastrearse hasta un proceso del DFD o un caso de uso. Si un componente no se rastrea, pregúntense por qué existe.
